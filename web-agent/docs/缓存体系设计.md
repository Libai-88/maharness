# maharness 缓存体系设计（v2）

> 目标：让「已被观察过的现实」不被重复计算——逼近 100% 命中率。
> 借鉴：GPTCache（语义缓存）、Redis/Caffeine（TTL 与淘汰）、prompt cache 分层（KV cache）、
> Claude Code 四层缓存架构、DeepSeek/OpenAI/Anthropic 前缀缓存官方实践。

## 〇、第一性原理：重复的两种本质与两层缓存

LLM 缓存从第一性原理看只有两种形态，它们互补而不重叠：

| 形态 | 缓存的本质 | 命中条件 | 命中效果 | 决定权 |
|---|---|---|---|---|
| **Provider 前缀缓存**（KV cache / context caching） | 计算中间态（token 的 K/V） | **逐 token 精确前缀匹配**（非语义） | 跳过 prefill 重算：省 input 钱与 TTFT，**输出照常生成、结果不变** | provider 说了算（usage 字段） |
| **应用侧语义缓存**（L1/L2） | 最终答案 / 工具结果 | 问题语义近似 / 键完全一致 | **整个调用被跳过**，省 100% 钱与延迟 | 应用自己说了算 |

**关键认知**：
1. 前缀缓存是**字节级精确匹配**——「1+2=3」能命中，「2+1=3」完全 miss。任何重排、增删、换行、空白、时间戳变化都破坏前缀。**命中率 = 请求序列稳定性**，与问题是否"相似"无关。
2. 真实命中率**只能从 provider usage 字段读取**：DeepSeek `prompt_cache_hit_tokens`、OpenAI/智谱 `prompt_tokens_details.cached_tokens`、Anthropic `cache_read_input_tokens`。本地估算（公共前缀 token 数）只能做事前预测与无反馈时的降级。
3. 两种缓存分工：语义缓存挡在最前（重复问题根本不产生调用），前缀缓存兜底长上下文（未命中的请求吃折扣）。**成本杠杆**：DeepSeek 命中/未命中价差 50~120 倍、OpenAI 最高省 90%、Anthropic read 为 1/10 价、Kimi 10 倍差——agent 多轮对话的成本大头在 input，前缀缓存健康 = 成本健康。

## 一、三层各自的任务

| 层 | 重复的本质 | 缓存什么 | 失效策略 |
|---|---|---|---|
| **L1 语义缓存** | 问题的重复 | 同一含义问题的 LLM 答案（作用域隔离：全局纯问答 / 会话自产） | TTL 24h + promptKey 隔离 + scope 隔离 |
| **L2 工具结果缓存** | 观察的重复 | 同一工具+同一参数的返回 | TTL 30min + 文件 mtime/size 校验 + LRU |
| **L3 prompt 前缀缓存** | token 的重复 | 多轮对话的公共前缀（provider KV cache） | 消息只追加不重写，前缀稳定；真实命中按 usage 统计 |

## 二、L1 语义缓存：轻量语义归一化（自研）

**核心洞察**：中文同义改写后，全文本 bigram 重合率天然低（实测 0.45-0.71），阈值 0.85 时**永远无法命中**。语义匹配必须忽略表面措辞：

1. **内容词过滤**（`contentWords`）：去标点空格 → 去中文功能词（的/了/吗/是/什么/帮我…，**多字词整词剔除、单字词逐字剔除**）→ 内容词序列。实测相似度大幅提升：Python 释义 0.563→0.846、PowerShell 释义 0.683→0.722。
2. **精确匹配优先**：归一化后全等的重复提问直接命中（O(1)），不走相似度。
3. **动作方向校验**（`actionGroups`）：内容相似但动作不同（写 vs 读）绝不能串答案——动词归一为语义类别（query/write/delete/execute），命中前比对类别集合。实测拦截「写快排→读快排」误命中（相似度 0.875 被正确拒绝）。
4. **阈值 0.58**：实测命中 0.667-0.846 的同义改写，拒绝 0.513 弱相关与 0.0 无关。
5. **命中学习**：命中时回填当前措辞（**沿用来源条目的作用域**）——语义缓存簇随使用扩展，第 3、4 种说法连续命中。
6. **promptKey 隔离**：systemPrompt 指纹分区——人设/插件/思考语言变化不串用旧答案。
7. **scope 作用域隔离（v2）**：答案分两种——**全局**（纯问答，历史无工具消息，任何会话可复用）与**会话**（答案依赖本会话工具观察，如"这个文件里写了什么"，仅本会话可命中）。防的是跨会话复用陈旧的工具观察（同一问题在文件变更后应重新观察，而不是复用旧答案）。**这也是对"历史有 tool 消息就不查 L1"这一过度保守条件的修正**：带 scope 查询后，工具会话内的重复/近似提问也能命中本会话自产答案，同时绝不跨会话串用。

**可选升级路径**：配置 EMBEDDING_* 后自动切换向量语义匹配（余弦 ≥ 0.95），覆盖完全改写的同义问题。

## 三、持久化：缓存必须比进程活得久

**洞察**：进程内缓存重启即清零，命中率必然归零——「逼近 100%」的前提是跨重启保留。

- 落盘 `data/cache.json`（L1 特征 + scope + L2 值，防抖 5s 保存，`kernel.stop()` 时强制落盘）
- 启动时恢复未过期条目（过期条目直接丢弃）
- 实测：写入 → 重启 server → 同义改写命中（cached: True，跨进程）

## 四、L2 工具结果缓存

- 已接入：`list_dir` / `read_file`（key = hash(工具+参数+mtime+size)，文件变更即时失效）、`web_search`（TTL 10min，v2 命名空间）
- 安全边界：只缓存**只读/确定性**工具；写操作永不缓存
- **命名空间失效（v2）**：key = `工具名:hash`（`makeKey(parts)` 自动加前缀）。写操作（write_file/delete_file）后只失效 `list_dir`/`read_file` 命名空间，**不再清空整个 L2**——web_search 等无关工具的缓存不受误伤
- **LRU 淘汰（v2）**：超容量（2000 条）淘汰**最久未访问**（按 lastAccess 字段），而非插入最早的 FIFO——热条目保得住，冷条目先走
- TTL 是防膨胀底线（文件类有 mtime 校验，TTL 只是保险）

## 五、L3 prompt 前缀缓存：真实命中原则

**v2 核心升级：从"估算"到"真实"**。

- 消息**只追加不重写**（历史不变、新消息追加）→ provider KV cache 前缀稳定命中
- 注入类消息（英文思考 Reminder、记忆、预算提示）固定在末尾，不破坏前缀
- **本地估算口径**（保留，降级用）：每轮与上一轮的公共前缀 token 数（`sharedPrefixTokens`）——只回答"预计命中多少"，无法确认 provider 是否真命中
- **真实口径**（v2，唯一权威）：provider usage 归一化后的缓存命中 token（`recordProviderCacheHit`）：
  - DeepSeek：`prompt_cache_hit_tokens` + `prompt_cache_miss_tokens`（和 = prompt_tokens）
  - OpenAI/智谱：`prompt_tokens_details.cached_tokens`；miss = prompt − cached
  - Anthropic：`cache_read_input_tokens`；miss ≈ input − cache_read
  - 真实命中率 = `l3RealTokens / (l3RealTokens + l3RealMissTokens)`
- **省钱核算（v2）**：L3 命中按 provider input 价格 × 命中 token 计入 savedCost（此前只算 L1 命中）——DeepSeek 语境下这是 50~120 倍杠杆，是 agent 成本的主战场
- **双口径对照**：估算值 ≫ 真实值时，说明前缀在本地看稳定但 provider 没命中——典型原因：TTL 过期（OpenAI 5-10min / Anthropic 5min）、provider 路由抖动、换模型/tokenizer、上下文压缩重写了历史。命中率应像 uptime 一样监控，骤降即前缀被改动的信号。

**缓存感知的 prompt 组装纪律**（厂商实践一致性结论：越静态越靠前、动态内容只追加）：
1. system prompt 组装顺序固定（人设 → 插件规则按 priority 降序），**绝不把时间/路径/随机内容写进 system**
2. 工具定义（tools 数组）在会话内冻结——不增删、不重排、确定性序列化；能力切换用 mode/子 agent
3. 动态注入（记忆、时间、预算提示）一律**追加在消息末尾**
4. 上下文压缩时**原前缀保持逐字节不变，摘要作为新消息追加**（cache-safe 压缩）
5. 会话内不换模型——缓存与模型/tokenizer 绑定，换模型 = 全量重建

## 六、命中率度量

- Trace：每次命中记录 `cache_hit` 步骤（L1/L2 均可观测）；`llm_call` 步骤记录 `tokensCached`（provider 确认的命中 token）
- Stats：L1 hits/misses/rate、L2 统计、**L3 双口径（估算 tokens + 真实 tokens/rate）**、overall（served/total/rate）、节省成本
- 前端：轨迹面板实时命中率 + 统计页三层缓存卡（L3 卡优先展示真实命中率）

## 七、实测结果

| 场景 | 结果 |
|---|---|
| 同义改写命中（列出↔查看） | ✅ cached: True |
| Python 释义（0.846 相似度） | ✅ 命中 |
| 写→读 方向拦截 | ✅ 不误命中 |
| 无关问题（0.0） | ✅ 不误命中 |
| 跨进程重启 | ✅ 磁盘恢复后命中 |
| 精确重复提问 | ✅ O(1) 命中 |
| 多字停用词整词剔除（为什么/什么…） | ✅ 修复前永不生效 |
| 作用域隔离：会话自产答案跨会话 | ✅ 不串用 |
| L3 真实命中统计（usage 归一化） | ✅ DeepSeek/OpenAI/Anthropic 三路归一 |
| L2 LRU：访问过的旧条目 | ✅ 保留（FIFO 会误杀） |
| L1 scope 跨重启恢复 | ✅ 持久化 roundtrip |
