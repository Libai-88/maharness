# maharness 积木哲学

> **核心理念**：除了 agent 运行时核心，maharness 中所有的一切都是插件。
> 包括前端——它只是插件的一部分。maharness 拥有修改 agent 核心之外的所有能力。
> 整个 maharness 是一块积木：它是什么样子，取决于用户想让它成为什么样子。

## 一、边界划分（唯一不可变的是运行时核心）

> **v3.3 更新（一切皆插件闭环）**：原先把 `core/chat` 的执行循环列为「不可修改的基座」，
> 并把 kernel 的 cache/trace/budget 当作不可替换的原语——这两处是「一切皆插件」最后
> 未闭环的地方。现已改为**服务化 + 优先级接管**：内核与内置插件只提供**默认实现**，
> 任何插件都能以更高优先级接管，卸载后自动回退。见下方第二节与第五节。

| 层级 | 内容 | 可修改性 |
|---|---|---|
| **agent 运行时核心** | kernel/（总线/配置/缓存/预算/Trace/插件加载/逆元作用域） | **不可修改**（积木的基座）；但其**子系统实现可被插件接管**（service:cache/trace/budget） |
| **执行循环** | 默认实现 core/chat/agent.ts；契约 kernel/loop.ts | **可被插件整体替换**（service:runner）——顶层/子代理/并行三路径同时生效 |
| 内置插件 | core/ 其余全部（search/powershell/tools-fs/self-extend/skills/…） | 可修改（改动经服务重启生效） |
| 用户插件 | plugins/ 现场目录 | 可修改 + 目录监听热重载 |
| **前端** | ui/（界面、主题、图标、面板） | 可修改（经前端构建生效）；**插件页面由插件声明 nav 自动成标签页**，前端无需改动 |
| 配置 | config.json / .env / DB | 可修改 + 热更新 |

**原则**：核心提供「运行时 + 修改一切的能力」；核心之外的每一块（能力、命令、人设、上下文、API、前端页面、**乃至执行循环与内核子系统**）都由插件提供或可被插件/用户修改。

## 二、插件能力全景（八种能力类型）

| 能力 | 用途 | 示例 |
|---|---|---|
| `tool` | LLM 工具 | list_dir / powershell_execute / create_plugin |
| `command` | 斜杠命令（命令面板） | 插件可注册自己的命令 |
| `listener` | 事件监听（钩子） | 插件响应 agent.* 事件 |
| `provider` | LLM Provider | chat 服务消费 |
| `service` | 对外服务实例 | chat 服务 |
| `persona` | 系统提示词片段（L2 层） | 自我扩展规则 |
| `context` | 上下文注入（Context Provider） | 长期记忆 |
| `role` | 专业化角色（handoff 目标） | 主代理 / 规划者 |
| **`api`** | **REST API + 前端页面** | 插件的 `/panel`、导航页 |
| **`nav`（声明）** | **前端顶层标签页** | 插件在 plugin.json 声明即拥有自己的一页 |

**前端页面贡献（v3.3，从「有数据通道」升级为「有自己的一页」）**：
- 插件在 `plugin.json` 声明 `nav: { label, icon, order, mode, page|panel, status? }`；
- 内核经 `navContributions()` 投影为清单，server 暴露 `GET /api/nav`；
- 前端遍历清单生成标签页，用**唯一一个**通用容器 `PluginTabView` 渲染：
  `mode:'iframe'` 嵌入插件完整页面（富交互保真），`mode:'panel'` 内联净化渲染片段；
- `status` 端点让插件在页头展示自己的实时状态——前端仍然不认识任何插件；
- **停用即下线**：未启动的插件不出现在清单里（与能力可见性同一规则）。

**执行循环与内核子系统的接管（v3.3，可组合性的最后闭环）**：
- `ctx.provide(key, value, priority)` 支持**同键多提供者并存**：priority 大者生效，
  同优先级先到者胜；**接管者卸载后自动回退**到次高者/内核内置实现（服务不消失）；
- 内核子系统（cache/trace/budget）以内置实现作为 priority 0 的默认提供者进入同一仲裁——
  内核不再垄断实现，且 `kernel.cache` 等访问器走解析层，**137 处调用点零改动**；
- 执行循环是 `service:runner`（工厂 `(kernel, bus) => { run, approveApproval }`）：
  默认实现由 core/chat 提供，任何插件可整体替换，且顶层对话/子代理/并行**三条路径
  统一经 `makeRunner()` 取循环**——不会出现「顶层换了、子代理还在跑旧循环」的割裂。

## 三、修改能力盘点（maharness 能改什么）

| 对象 | 通道 | 生效方式 |
|---|---|---|
| 插件 | create_plugin / write_file（plugins/） | 目录监听热重载 |
| 内置插件 | write_file（core/） | 服务重启 |
| 前端 | write_file（ui/src/） | 前端构建 / vite dev 热更新 |
| 环境变量 | write_file（.env） | .env 监听 → 刷新 env → 重载全部插件 |
| 配置 | config.json / /api/config | config.changed 热更新 |
| 数据库 | DB API | 即时 |
| 技能 | skills 市场安装/卸载 | 即时 |

**结论**：maharness 拥有修改 agent 核心之外一切的能力，且大部分通道支持热更新——「积木」可塑性完整。

## 四、理念符合性审查（2026-08-16）

| 审查项 | 结论 |
|---|---|
| LLM 工具 100% 来自插件 | ✅ capabilities('tool')，内核零硬编码 |
| 命令插件化 | ✅ command 能力 + 内置/插件命令合并 |
| 人设/上下文插件化 | ✅ persona / context 能力 |
| **插件提供 REST API** | ✅ api 能力 |
| **插件贡献前端 UI** | ✅ **插件声明 nav 即拥有顶层标签页**；通用容器渲染，前端零插件知识 |
| **执行循环可替换** | ✅ **service:runner**；顶层/子代理/并行三路径统一经 makeRunner 取循环 |
| **内核子系统可替换** | ✅ cache/trace/budget 以 priority 0 默认实现入仲裁，插件可接管（137 处调用点零改动） |
| **服务可接管不互相覆盖** | ✅ 同键多提供者并存 + priority 仲裁 + 卸载自动回退（修复了旧实现的静默顶掉/连带删除） |
| server 无业务逻辑 | ✅ 纯路由（历史端点保留，新能力走插件） |
| core/ vs plugins/ 分层 | ✅ 信任分层非能力分层（同一套机制） |
| **可逆性边界** | ✅ 界内（ctx.* 副作用）运行时自动回滚；界外（文件/DB/网络）由插件自备补偿——契约已文档化 |
| 自我扩展边界 | ✅ 内核代码不可改，但内核**行为**可经服务接管改变；core/ 其余与 ui/ 可改 |

## 五、遗留路线（不阻塞，记录）

1. **前端组件级插件化（部分完成）**：现已支持插件贡献顶层标签页（iframe 完整页 / panel 片段），
   但插件仍无法向前端贡献 **React 组件**（如需与宿主状态深度互操作的视图，仍需改前端 shell）。
   下一步：插件注册前端模块（动态 import + 宿主协议）。
2. **server 历史端点迁移**：git/config/meta 等端点本质是能力，可逐步迁移为插件（api 能力已就绪，迁移时无需改前端）。
3. **内置命令插件化**：BUILTIN_COMMANDS 可下沉为「核心交互插件」，低优先级。
4. **内置标签页插件化**：`files`（文件工作区）目前仍是前端内置标签页（未走 nav 声明）——
   它是核心 UI 而非插件能力，若要彻底统一可把它也改成内置插件并声明 nav。
5. **WorkbenchView 组件退役**：其通用部分已由 PluginTabView 取代（工作台标签页改用 nav 声明 +
   `/status` 状态端点）；`ui/src/components/WorkbenchView.tsx` 与 `TodoBoardView.tsx` 已不再被引用，
   可删除（保留会让人误以为前端仍需为插件写组件）。
