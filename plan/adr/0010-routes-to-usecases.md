# ADR 0010：路由只做协议，编排下沉到 usecases

## 背景

`server/routes/` 有 30 个文件，`server/routes/shared.ts` 506 行同时装着 SSE、SSRF 校验、密钥擦除、git/文件命令执行、租户与工作区作用域。部分路由直接编排多个服务（例如组织、社会、任务的组合动作），导致：同一段业务在 HTTP 与测试/脚本里各写一遍；路由文件按业务越长越大；"这条规则到底在哪执行"无法回答。

## 决策

1. 新增 `server/usecases/`：一个用例 = 一次用户意图的完整编排（含前置校验、跨服务调用、事务边界、事件发布）。用例不碰 HTTP 对象，不拼 SQL。
2. `routes/` 只做四件事：解析请求 → 调 `usecases.<x>` → 映射响应/错误码 → 鉴权与租户作用域。
3. `routes/shared.ts` 按关注点拆为四块：`sse.ts`（事件流）、`security.ts`（SSRF、密钥擦除）、`exec.ts`（git 与文件命令）、`scope.ts`（租户/工作区/角色）。
4. **边界可执行**：新增 AST 边界测试，禁止 `routes/*` 直接 import `server/services/*`（必须经 `usecases`），与既有 kernel、server→core 两条边界同构。
5. 单 route 文件上限 250 行；超限说明编排没有下沉。

## 后果

- 路由文件回到"协议适配器"尺寸；同一业务可在测试、脚本、CLI 复用同一用例。
- `shared.ts` 的口袋效应消失，安全相关代码有了明确归属（`security.ts`）。
- 代价是多一层跳转；为控制这一点，只对"跨 ≥2 个服务或含事务"的业务建用例，单服务只读查询仍可由路由直接调服务（由边界测试白名单显式登记）。
- 风险：误把事务边界搬进用例会改变提交时机。约束是用例只调用已存在的事务方法，不自行开新事务。

## 回滚

用例层是纯新增：回滚只需把路由改回直连服务，并删除边界测试白名单外的用例文件。
