# ADR 0009：契约单一来源与前端类型生成

## 背景

`ui/src/types.ts`（630 行）与 `ui/src/api.ts`（628 行）手工维护着与服务端同名的 API 形状。服务端改一个字段，前端靠人记得同步；`check-doc-facts` 只校验 6 个字段，其余全靠运气。同类问题已经发生过一次（P2-4 插件导入路径的文档漂移），只是那次漂移的是文档而不是类型。

## 决策

1. **单一来源**：`web-agent/contracts/api.ts` 是 API 线上形状的唯一声明处。它只允许包含类型与常量，**不得 import 任何运行时模块**（保证可被逐字复制而不会带入服务端依赖）。
2. **生成物**：`ui/src/generated/contracts.ts` 由 `scripts/check-contracts.mjs --write` 逐字生成，带"请勿手改"横幅；CI 校验与源逐字一致，不一致即失败。
3. **前端共享类型改指向生成物**：`ui/src/types.ts` 保留 UI 专有类型，凡与服务端同名同形的类型改为 `export type { X } from './generated/contracts'`，不再手写第二份。
4. **服务端对齐由测试保底**：`server/tests/contracts.spec.ts` 对真实响应样本做形状断言，并用类型赋值检查把路由/存储产出对齐到契约；契约改动必须先过该用例。

## 后果

- 契约漂移从"人记得同步"变成 CI 失败；前端不再存在第二份 API 定义。
- 生成物是纯类型文件，Vite 构建时被完全擦除，无运行时成本。
- 代价：契约改动需两次动作（改源 + 生成），但第二次由脚本完成；服务端若出现契约未覆盖的新字段，需要显式加入契约（这正是想要的阻力）。
- 不做的事：不引入 OpenAPI/代码生成框架（内部单机 API，收益低于维护成本）。

## 回滚

删除生成物与门禁、恢复手写类型即可；服务端代码不受影响。
